# Riverpod Architecture Testing Guide

Testing is a critical part of developing robust, production-ready Flutter applications. This guide explains how to thoroughly test a Riverpod-based, feature-first application layer by layer.

## The Core Philosophy: AAA

Every good test follows the **Arrange, Act, Assert (AAA)** pattern:
1. **Arrange**: Set up the environment, fake data, and mock responses.
2. **Act**: Execute the specific function or trigger the state change you want to test.
3. **Assert**: Verify that the outcome matches your expectations.

## 1. Unit Testing the Domain Layer (Models)

The domain layer contains your pure data models (often generated by `Freezed`). These are the easiest to test because they have no dependencies.

**Goal:** Ensure that JSON parsing maps to your Dart objects correctly and that default values hold up.

```dart
test('should parse JSON properly', () {
  // 1. Arrange
  final jsonMap = {
    'id': 1,
    'title': 'Test',
    'completed': false,
    'userId': 1,
  };

  // 2. Act
  final todo = Todo.fromJson(jsonMap);

  // 3. Assert
  expect(todo.id, 1);
  expect(todo.completed, false);
});
```

## 2. Unit Testing the Data Layer (Repositories)

Repositories sit between your application logic and the outside world (APIs, databases). We **never** want our tests to make real network requests. Instead, we use `mocktail` to create fake versions of our dependencies (like `ApiClient`).

**Goal:** Ensure the repository properly transforms raw data (like JSON from an API) into Domain models, and correctly throws errors when the API fails.

```dart
// Create a fake version of your dependency
class MockApiClient extends Mock implements ApiClient {}

void main() {
  late MockApiClient mockApiClient;
  late TodoRepository todoRepository;

  setUp(() {
    mockApiClient = MockApiClient();
    // Inject the fake client into the real repository
    todoRepository = TodoRepository(mockApiClient);
  });

  test('should return a list of todos on success', () async {
    // Arrange: Tell the mock how to behave when asked
    when(() => mockApiClient.get(any())).thenAnswer((_) async => [
      {'id': 1, 'title': 'Test', 'completed': false, 'userId': 1},
    ]);

    // Act
    final todos = await todoRepository.getTodos();

    // Assert
    expect(todos, isNotEmpty);
    expect(todos[0].title, 'Test');
    
    // Verify the mock was actually called
    verify(() => mockApiClient.get(any())).called(1);
  });
}
```

## 3. Unit Testing the Application Layer (Riverpod Providers)

This is where Riverpod testing shines. Unlike BLoC, where you test a standalone class, Riverpod providers are global and need an environment to run in. We provide this environment using a `ProviderContainer`.

### The Magic of `ProviderContainer` and `overrides`
A `ProviderContainer` is essentially a headless `ProviderScope`. It holds the state of your app in memory.
When testing, we don't want our providers to use the *real* repository. We use the `overrides` list to intercept the dependency tree.

**Goal:** Ensure your `Notifier` or `AsyncNotifier` transitions states correctly (Loading -> Data -> Error) and modifies state properly when methods are called.

```dart
class MockTodoRepository extends Mock implements TodoRepository {}

void main() {
  late MockTodoRepository mockRepository;
  late ProviderContainer container;

  setUp(() {
    mockRepository = MockTodoRepository();
    
    container = ProviderContainer(
      overrides: [
        // INTERCEPT: Whenever ANY provider asks for the repository, 
        // give them the mock instead of the real one!
        todoRepositoryProvider.overrideWithValue(mockRepository),
      ],
    );
  });

  tearDown(() {
    container.dispose(); // Always clean up memory between tests
  });

  test('addTodo appends a new todo to the state', () async {
    // Arrange
    final initial = [Todo(id: 1, title: 'Old', completed: false, userId: 1)];
    final newTodo = Todo(id: 2, title: 'New', completed: false, userId: 1);
    
    when(() => mockRepository.getTodos()).thenAnswer((_) async => initial);
    when(() => mockRepository.createTodo('New')).thenAnswer((_) async => newTodo);

    // Act 1: Wait for initial load
    await container.read(todoListProvider.future);
    
    // Act 2: Trigger our custom method
    await container.read(todoListProvider.notifier).addTodo('New');

    // Assert: Read the updated state
    final state = container.read(todoListProvider).value!;
    expect(state.length, 2);
    expect(state.last.title, 'New');
  });
}
```

## 4. Widget Testing the Presentation Layer (UI)

Widget testing verifies that your UI renders correctly based on the Riverpod state.
Instead of a `ProviderContainer`, we use a real `ProviderScope` wrapped around our test widget.

**Goal:** Ensure that the UI displays the correct widgets (like `CircularProgressIndicator` or `ListView`) based on the mocked state, and that buttons trigger the correct actions.

```dart
testWidgets('Displays list of todos when state has data', (tester) async {
  // Arrange
  final mockRepository = MockTodoRepository();
  final fakeTodos = [Todo(id: 1, title: 'UI Test', completed: false, userId: 1)];
  
  when(() => mockRepository.getTodos()).thenAnswer((_) async => fakeTodos);

  // Act: Pump the widget into the test environment
  await tester.pumpWidget(
    ProviderScope(
      overrides: [
        // We override the repository at the root of the app!
        todoRepositoryProvider.overrideWithValue(mockRepository),
      ],
      child: const MaterialApp(
        home: HomeScreen(),
      ),
    ),
  );

  // Assert: Initially it should be loading
  expect(find.byType(CircularProgressIndicator), findsOneWidget);

  // Act: Wait for the FutureProvider to resolve
  await tester.pumpAndSettle();

  // Assert: The list should now be visible
  expect(find.text('UI Test'), findsOneWidget);
  expect(find.byType(Checkbox), findsOneWidget);
});
```

### Testing `.family` Providers
When testing a `Provider.family` or `FutureProvider.family`, you simply pass the argument when reading it from the container:
```dart
// The ID (99) is the family argument
final todo = await container.read(todoDetailProvider(99).future);
```

### Simulating User Interactions & Form Validation
You can use the `tester` to simulate typing and tapping, and then verify the UI reacts (like showing a red validation error).
```dart
// Type into a TextFormField
await tester.enterText(find.byType(TextFormField), 'New Todo');

// Tap a button
await tester.tap(find.byType(ElevatedButton));

// Wait for animations and futures to finish
await tester.pumpAndSettle(); 

// Assert a validation error appears on the screen
expect(find.text('Please enter a title'), findsOneWidget);

// Assert a method was NEVER called due to validation failing
verifyNever(() => mockRepository.createTodo(any()));
```

### Dealing with Navigation (GoRouter) in Tests
If your widget calls `context.pop()` or `context.push()`, wrapping it in a standard `MaterialApp()` will crash your test with `No GoRouter found in context` or `There is nothing to pop`. 

**Solution 1**: Always provide a mini `GoRouter` to your test widget:
```dart
Widget createWidgetUnderTest() {
  final router = GoRouter(
    routes: [
      GoRoute(path: '/', builder: (context, state) => const MyScreen()),
    ],
  );
  return ProviderScope(
    child: MaterialApp.router(routerConfig: router),
  );
}
```

**Solution 2 (Best Practice)**: Guard your pop calls in production code!
```dart
if (context.mounted && context.canPop()) {
  context.pop();
}
```

## Summary
- **Domain**: Test pure Dart parsing (`fromJson`).
- **Data**: Test Repository logic using a Mocked HTTP Client.
- **Application (Riverpod)**: Test Provider state changes using a `ProviderContainer` with mocked Repository overrides.
- **Presentation**: Test UI rendering, interactions, and validation using a `ProviderScope` with mocked Repository overrides.
